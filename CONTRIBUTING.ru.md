# Контрибьютинг в testaipack

Этот документ фиксирует рабочие правила проекта. Цель — сократить rework (повторные правки после review/verify) и держать контракт и impl в синхронизации. Правила применяются к каждому PR.

> Контекст: aiStats показал высокий уровень rework-loop'ов («файлы revisited после verify/review/fix»). Причина — слабый spec/context up front. Эти правила делают наоборот: максимум определённости до первой правки.

---

## 1. TDD-дисциплина (обязательно)

- **Тесты ПЕРВЫМИ.** Любая правка начинается с красного теста, который воспроизводит поведение, которое нужно добавить или починить. Сначала тест падает, потом пишется impl, потом тест зеленеет.
- **Coverage ≥80%** по каждому модулю. CI блокирует слияние при падении порога.
- **Не писать impl до теста.** Если правка не покрывается тестом — это рефакторинг или документация, и это нужно явно отметить в PR.

---

## 2. Контракты первичны

- Любое изменение поведения начинается с правки `contract/*.tsp` → `tsp compile` → codegen → потом impl. Контракт описывает wire-format и является единым источником правды для типов и Zod-схем.
- **Не менять сгенерированные файлы в `src/generated/` руками.** Они перегенерируются из TypeSpec на `npm run contract:codegen` (а также на `npm install` через `prepare`).
- TypeSpec = единый источник правды. Если тип нужен в impl — добавляй его в контракт, потом codegen, потом импортируй из `@generated/types` или `@generated/schemas`.

---

## 3. Перед impl — фаза Planning

До первой правки кода:

1. Прочитай phase-док (`docs/phases/NN-*.ru.md`) целиком — там алгоритм, edge-cases, ссылки на контракт.
2. Прочитай контракт (`contract/phases/NN-*.tsp`) — входы, выходы, коды ошибок.
3. Составь список edge-cases из секции 5 phase-дока (обычно «Edge cases / corner cases»). Это станет тестами.
4. **Time-box: не больше 30 минут** на research перед первой правкой. Если за 30 минут не ясно — задай вопрос, не уходи в бесконечный ресёрч.

---

## 4. Анти-rework правила

- **Не править файлы повторно после review без обновления теста.** Если review нашёл баг — сначала воспроизведи его тестом (красный), потом фикс.
- **Каждый PR должен проходить `typecheck` + `lint` + `test` локально перед push.** Не пушь красное.
- **Если fix-phase занимает >2× impl-time — остановись и пересмотри подход.** Скорее всего, spec был неполным или выбран неверный путь. Лучше вернуться к контракту/phase-доку, чем бесконечно латать.
- **Не дублируй существующий код.** Перед написанием новой утилиты/функции — `grep` по репо. Возможно, она уже есть (например, git-обёртки в `src/util/git.ts`, fs-операции в `src/util/fs.ts`).

---

## 5. Стиль кода

- **TypeScript strict** (`strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`). Никаких `any` / `as` / `!` без обоснования в комментарии (и комментарий должен объяснять, почему unsafe-assertion безопасно).
- **Effect-TS** для IO и типизированных ошибок: `Effect.gen`, `Effect.fail`, tagged errors (`Data.TaggedError`). См. `src/errors.ts`, `src/util/git.ts`, `src/util/fs.ts` за образцом.
- **Co-located тесты** (`*.test.ts` рядом с модулем). Не складывать все тесты в `tests/`.
- **JSDoc только WHAT** (что функция делает), одной строкой. **Никогда WHY / история / какой баг фиксит** — это гниёт и относится в PR description. Если имя функции уже говорит что она делает — JSDoc не нужен.

---

## 6. Структура PR

- **Один PR = одна фаза или одна связная фича.** Не мешать фазы в одном PR.
- **Тесты и impl в одном PR.** Не открывать PR «сначала тесты, потом impl».
- **Обновление контракта отдельным коммитом** внутри PR: сначала коммит `contract: ...` (правка `.tsp` + перегенерация), потом коммиты с impl. Так ревьюер видит, где меняется wire-format.
- PR description заполняется по шаблону `.github/PULL_REQUEST_TEMPLATE.md`.

---

## Команды

```bash
npm install                  # зависимости + codegen (через prepare)
npm run contract:codegen     # перегенерировать src/generated/ из TypeSpec
npm run typecheck            # tsc --noEmit
npm run lint                 # eslint --max-warnings=0
npm test                     # vitest run
npm run test:coverage        # vitest с покрытием (≥80% gate)
npm run build                # → dist/testaipack (нужен bun)
```

Перед push: `npm run typecheck && npm run lint && npm test` — всё должно быть зелёным.

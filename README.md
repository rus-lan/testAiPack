# testaipack

**N-way A/B/…-тестер для opencode-интеграций.** Сравнивает работу AI-агента в
произвольном числе конфигураций («вариантов») — например «чистый агент» vs
«агент + skill A» vs «агент + skill B»: клонирует репозиторий, прогоняет один
и тот же промпт на каждом варианте, собирает метрики (токены, время,
стоимость, шаги) и рендерит сравнительный отчёт каждого варианта против
одного назначенного baseline.

Создано для тех, кто поддерживает opencode-пакеты и хочет измерить их реальный
вклад — не на глаз, а в числах с медианой по N прогонам и критерием
значимости.

Классический двусторонний сценарий («до/после установки одного пакета») никуда
не делся — это по-прежнему самый быстрый путь через флаги `--pack`/`--prompt`/
`--pure-baseline` (см. [«Быстрый старт»](#быстрый-старт)); он ровно
desugar-ится в два варианта `old`/`new` под капотом. N-way — надстройка поверх
той же машины, а не отдельный режим: `variants`/`packs` в
`.testaipack/config.json` (см. [«N-way варианты»](#n-way-варианты-variants-в-configjson)).

## Возможности

- **Полный N-way цикл** в одной команде: клон репо → установка паков →
  N прогонов на каждый вариант → агрегация → diff → отчёт против baseline.
- **Произвольное число вариантов**: от классической пары `old`/`new` до
  сколь угодно длинного списка именованных конфигураций, каждая — со своим
  набором паков, своим промптом/init/model/hint/verify.
- **Любой тип пака**: skill, plugin, agent, command, mcp — тип определяется
  автоматически по `ref`.
- **Изоляция окружения**: фейковый `$HOME` без сторонних плагинов/скиллов
  (`--isolation=home`) или throwaway Docker-контейнер (`--isolation=docker`).
- **Усреднение по медиане**: несколько прогонов на вариант, правило 1.5×IQR
  (против IQR baseline-варианта) для определения значимости дельт.
- **Контроль модели прогона**: `--model` (или per-variant `model` в конфиге)
  фиксирует модель и проверяется preflight-ом до дорогих N-вариантных прогонов
  — не только на глаз после того, как прогон уже упал.
- **Мультиформатный отчёт**: Markdown, HTML, JSON, YAML — выберите любой набор;
  таблицы metric-major — одна строка на пару (метрика, вариант), baseline
  первым в каждой группе.
- **LLM-судья** (опционально): единый вызов оценивает все варианты сразу
  (с попарным фолбэком при переполнении контекста), ранжирует и объясняет.
- **Cross-run сравнение**: команда `compare` сопоставляет любые два прогона по
  имени варианта («pack-X неделю назад vs сейчас», «pack-X vs pack-Y»).
- **Inspect-friendly результат**: multi-root VSCode workspace открывается одной
  командой `review` — все варианты и все паки side-by-side.
- **Контракт-first**: TypeSpec-контракт как единый источник правды для типов и
  Zod-схем; `src/generated/` никогда не правится руками.
- **Старые прогоны продолжают открываться**: воркспейсы, сделанные до
  появления N-way variants, читаются через совместимость на лету — `report
  --rebuild`, `compare`, `list` работают на них как прежде.

## Требования

- **opencode** — тестируемый AI-агент (запускается под капотом).
- **Node.js** `>=22` — для зависимостей и tooling.
- **bun** `>=1.1` — для сборки бинарника (`npm run build`).
- **git** — клонирование репозиториев.
- **docker** *(опционально)* — только для `--isolation=docker`.

Проверить всё разом: [`testaipack doctor`](#setup).

## Установка

### Через 1 команду (рекомендуется)

```bash
curl -fsSL https://github.com/rus-lan/testAiPack/releases/latest/download/install.sh | sh
```

Скрипт определит платформу (linux/darwin/windows × x64/arm64), скачает
бинарник из [последнего релиза](https://github.com/rus-lan/testAiPack/releases/latest)
и установит его в `~/.local/bin/testaipack`. Если каталога нет в `PATH` —
подскажет, какую строку добавить в rc-файл оболочки. Скачанный бинарник
сверяется с `checksums-sha256.txt` из того же релиза; при несовпадении
установка прерывается. Скачивание идёт напрямую через
`releases/latest/download/<asset>` — без обращений к GitHub API, так что
никакой rate limit скрипту не грозит.

Поставить конкретную версию вместо latest или сменить каталог установки:

```bash
TESTAIPACK_VERSION=0.5.0 sh install.sh
INSTALL_DIR=/opt/bin sh install.sh
```

Проверка checksum обязательна: если в окружении нет `sha256sum`/`shasum`,
скачать `checksums-sha256.txt` не вышло или в нём нет строки для нужного
бинарника — установка прерывается. Обойти это (например, в минимальном
окружении без sha256-утилит) можно через:

```bash
TESTAIPACK_SKIP_CHECKSUM=1 sh install.sh
```

### Готовый бинарник из releases

Скачайте бинарник для своей платформы со
[страницы релизов](https://github.com/rus-lan/testAiPack/releases/latest) и
положите `testaipack` в `PATH`. Бинарник self-contained (скомпилирован через
`bun build --compile`).

#### Платформы

| Платформа                  | Файл                       | Статус                                  |
| -------------------------- | -------------------------- | --------------------------------------- |
| Linux x64                  | `testaipack-linux-x64`     | ✅ runtime verified                     |
| Linux arm64                | `testaipack-linux-arm64`   | ⚠ собран, формат проверен (без runtime) |
| macOS x64 (Intel)          | `testaipack-darwin-x64`    | ⚠ собран, формат проверен (без runtime) |
| macOS arm64 (Apple Silicon)| `testaipack-darwin-arm64`  | ⚠ собран, формат проверен (без runtime) |
| Windows x64                | `testaipack-windows-x64.exe` | ⚠ собран, формат проверен (без runtime) |

Все бинарники — standalone (не требуют установленного runtime); SHA256-контрольные
суммы лежат рядом в `checksums-sha256.txt`.

### Из исходников

```bash
git clone https://github.com/rus-lan/testAiPack.git
cd testAiPack
npm install                  # только зависимости — codegen НЕ запускается сам
npm --prefix contract install
npm run contract:codegen     # обязательный шаг: сгенерировать src/generated/ из TypeSpec
npm run build                # → dist/testaipack (нужен bun)
```

После сборки бинарник лежит в `./dist/testaipack`. Для кросс-компиляции всех
платформ разом: `npm run build:all` (→ `dist/release/`).

### Проверка установки

```bash
testaipack doctor     # opencode, git, node, docker — всё на месте?
```

`doctor` заодно проверяет `bun`, но только информационно (`warn`, не `fail`) —
собранному бинарнику `bun` не нужен вообще, он важен только для сборки из
исходников (`npm run build`).

### Docker-изоляция (опционально)

Для `--isolation docker` нужен локальный образ с предустановленным opencode —
публичного образа `opencode/opencode:*` в Docker Hub нет, поэтому соберите его
один раз:

```bash
bash scripts/build-docker-image.sh
```

Скрипт соберёт образ `testaipack-opencode:latest` (ставит opencode из GitHub
releases поверх `node:22-slim`) и проверит, что `opencode --version` работает.
Версия opencode внутри образа зафиксирована явно (`ARG OPENCODE_VERSION` в
`Dockerfile.opencode`, сейчас `1.18.4`) — образ больше не тянет
`releases/latest` при каждой пересборке, так что пересборка не подсунет
незамеченную более новую версию. Собрать на другой версии для теста:
`bash scripts/build-docker-image.sh testaipack-opencode latest 1.18.9`
(или `docker build --build-arg OPENCODE_VERSION=1.18.9 ...` напрямую, не
трогая файл). После этого:

```bash
./dist/testaipack run <repo> \
  --isolation docker \
  --docker-image testaipack-opencode:latest \
  --pack ... --prompt ...
```

При недоступном Docker daemon (`docker info` не отвечает) фаза 00 автоматически
откатится на `home`-изоляцию и напечатает предупреждение в stderr — прогон не
станет docker-изолированным незаметно для пользователя. Если образ не собран,
preflight (gate 1) выдаст понятную ошибку с подсказкой собрать его через
`bash scripts/build-docker-image.sh` или переопределить через `--docker-image`.

Чтобы достучаться из контейнера до локального модельного сервера (например
ollama), нужен отдельный флаг `--docker-network host` — см. раздел «Локальные
/ self-hosted модели» ниже, там разобрано подробно и с оговоркой про Mac/Windows.

## Быстрый старт

Минимальный прогон требует только `<repo>` и `--prompt`. Остальные флаги имеют
дефолты (см. [таблицу ниже](#параметры-команды-run)).

```bash
# 1. Прогнать первый A/B (pack = skill из git-URL)
./dist/testaipack run https://github.com/owner/repo \
  --pack git+https://github.com/me/my-skill \
  --prompt "реализуй фичу X по спецификации"

# 2. Открыть результат в VSCode (multi-root workspace, old/new side-by-side)
./dist/testaipack review
```

Первый прогон создаст `./.testaipack/` с деревом рабочих директорий и положит
отчёт в `./.testaipack/<run-id>/results/` (см. [структуру результатов](#структура-результатов)).

> Smoke-test без пакета: `testaipack run <repo> --prompt "do the thing"` —
> оба варианта (`old`/`new`) всё равно прогоняются, оба без пака (реестр
> паков пуст) — единственная разница между ними остаётся в `pure`-режиме.

## Максимальный запуск

Полный пример со всеми осмысленными флагами:

```bash
./dist/testaipack run https://github.com/owner/repo \
  --pack git+https://github.com/me/my-skill \
  --pack-type skill \
  --prompt @prompts/build.md \
  --init @prompts/init.md \
  --verify "npm test && npm run lint" \
  --isolation home \
  --docker-image testaipack-opencode:latest \
  --docker-network host \
  --opencode-version 0.5.0 \
  --auth aws --auth ssh --auth git \
  --pure-baseline \
  --runs 5 \
  --parallel 2 \
  --baseline old \
  --hint "Если в проекте есть подготовленный индекс кода в .graphify/, используй его." \
  --judge @prompts/judge.md \
  --model anthropic/claude-sonnet-4-5 \
  --preflight-model anthropic/claude-3-5-haiku-20241022 \
  --format md --format html --format json \
  --output ./.testaipack/last/report \
  --diff-html \
  --collapse-repeats \
  --timeline-mode side-by-side \
  --timeout-preflight 60 \
  --timeout-run 900 \
  --timeout-verify 300 \
  --timeout-install 300 \
  --watchdog 90 \
  --timeout-total 3600 \
  --workspace ./.testaipack \
  --config ./.testaipack/config.json \
  --review-run 1 \
  --ide vscode \
  --pricing-path ./pricing.json \
  --log-level info \
  --ephemeral
```

`--parallel`, `--baseline` и `--hint` — глобальные флаги, они допустимы и в
этом классическом двустороннем сценарии (легаси-шим): `--parallel` ограничивает,
сколько вариантов гоняются одновременно (здесь их всегда 2 — `old`/`new`,
дефолт `--parallel 2` воспроизводит сегодняшнее поведение без флага),
`--baseline` в легаси-режиме всегда `old` и переопределять его смысла нет,
`--hint` — новое каноническое имя для `--pack-hint` (см. таблицу ниже). Для
сравнения больше чем двух конфигураций одновременно смотрите следующий раздел.

## N-way варианты (`variants` в config.json)

Флаги выше (`--pack`, `--prompt`, `--pure-baseline`, `--init-side`, …) под
капотом строят ровно **два** варианта — `old` (чистый baseline) и `new`
(baseline + один pack). Это остаётся основным путём для «до/после одного
пакета» и никуда не денется. Но у инструмента есть второй, config-only режим:
список произвольного числа именованных **вариантов** плюс общий **реестр
паков**, из которого варианты берут ссылки по имени. Режим включается одним
присутствием ключа `variants` в `.testaipack/config.json` — отдельного флага
для него нет.

Сохраните как `.testaipack/config.json` — файл читается через обычный
`JSON.parse`, без поддержки комментариев, так что ниже валидный чистый JSON:

```json
{
  "repoUrl": "https://github.com/owner/repo",
  "prompt": "составь подробную карту проекта и сохрани её в файл MAP.md",
  "verify": "npm test",
  "runs": 3,
  "parallel": 2,
  "baseline": "old",
  "packs": [
    { "name": "graphify", "ref": "https://github.com/Graphify-Labs/graphify", "type": "all" },
    { "name": "ast-grep", "ref": "npm:ast-grep-mcp" }
  ],
  "variants": [
    { "name": "old", "packs": [] },
    { "name": "graphify", "packs": ["graphify"] },
    {
      "name": "ast-grep",
      "packs": ["ast-grep"],
      "hint": "Если доступен ast-grep, используй его для структурного поиска по коду вместо grep."
    },
    {
      "name": "both",
      "packs": ["graphify", "ast-grep"],
      "hint": "Если доступны graphify и ast-grep, используй оба: graphify — для карты проекта, ast-grep — для структурного поиска."
    }
  ]
}
```

Вариант `both` объявляет **два** пака сразу (`packs: ["graphify",
"ast-grep"]`) — на одном варианте разрешено произвольное число паков, оба
устанавливаются в его HOME и оба проверяются preflight-гейтами независимо.

```bash
./dist/testaipack run --config ./.testaipack/config.json
```

Сравните с тем же экспериментом через классические флаги — эквивалент выше
для ДВУХ вариантов выглядел бы так (третий вариант через флаги в принципе не
выразим — легаси-поверхность жёстко ограничена парой):

```bash
./dist/testaipack run https://github.com/owner/repo \
  --pack "https://github.com/Graphify-Labs/graphify" --pack-type all \
  --prompt "составь подробную карту проекта и сохрани её в файл MAP.md" \
  --verify "npm test" --runs 3
```

Ключевые поля:

| Поле | Смысл |
| --- | --- |
| `packs[]` | Реестр паков эксперимента: `{ name, ref, type?, setup?, check? }`. `setup`/`check` теперь принадлежат ПАКУ (устанавливаются/проверяются один раз на каждую пару «объявивший вариант, pack»), а не варианту. |
| `variants[]` | Список плеч эксперимента: `{ name, packs: [...], prompt?, init?, model?, hint?, pure?, verify?, exercise?, allowPacks? }`. `packs` — имена из реестра выше. |
| `variants[].prompt/init/model/hint/verify` | Переопределяют одноимённое глобальное поле для этого варианта. Отсутствие поля наследует глобальное значение; явная пустая строка (`""`) явно ОТКЛЮЧАЕТ наследование — единственный способ сказать «у этого варианта нет init/hint/verify, даже если у остальных есть». |
| `variants[].pure` | Управляет чистотой окружения (`OPENCODE_PURE` и парные флаги). По умолчанию — `true`, если у варианта нет паков, `false`, если есть хотя бы один. |
| `variants[].exercise` | Преемник `--pack-exercise`, теперь per-variant: shell-команда, прогоняющая pack-пайплайн один раз на каждый прогон ЭТОГО варианта. |
| `variants[].allowPacks` | Имена паков, чей `check` разрешено «неожиданно» пройти в HOME этого варианта без провала preflight-гейта (преемник `--allow-baseline-tool`, теперь per-(вариант, pack)). |
| `baseline` | Имя варианта-эталона — все остальные сравниваются против него. По умолчанию — имя первого варианта в списке. |
| `parallel` | Максимум вариантов, гоняемых одновременно (см. флаг `--parallel` ниже). |
| `hint` (верхнего уровня) | Глобальный дефолт-hint для вариантов без собственного `hint`. |

**Число паков на вариант не ограничено.** Один и тот же пак дважды на одном
варианте (`packs: ["p1", "p1"]`, в том числе через два bare-ref, резолвящихся
к одному derived-имени) — всегда опечатка, а не «объявить сильнее», поэтому
отклоняется явно, а не молча дедуплицируется: `E_CONFIG_INVALID`
(`duplicate-pack-in-variant`).

**Два пака одного варианта не должны регистрировать одну и ту же вещь.**
Если оба целятся в один и тот же skill/agent/command/mcp-сервер/npm
plugin-модуль (агент и команда с ОДИНАКОВЫМ именем — не коллизия, они живут в
разных секциях), прогон падает ДО того, как HOME хоть одного варианта
построен, называя оба пака: `E_PACK_INSTALL_FAILED`. Это намеренно, не
ограничение: коллизия на внешнем ресурсе почти всегда конфликт авторства
конфигурации, а не осознанный шаринг — для шаринга уже есть штатный
механизм, один пак реестра, на который ссылаются `packs` НЕСКОЛЬКИХ
вариантов. Даже если оба пака доставляют байт-в-байт идентичный npm-модуль
(применение любого из двух было бы идемпотентным) — всё равно fail-loud, а не
тихий no-op. Харнесс-агент `build` защищён тем же механизмом: пак,
доставляющий агента по имени `build`, тоже падает как коллизия.
Setup нескольких паков одного варианта гоняется строго последовательно, в
порядке `variant.packs` (порядок объявления на самом варианте, а не порядок
реестра `packs[]`).

**Смешивать `variants` с легаси-флагами, формирующими варианты, нельзя.**
Конфиг с ключом `variants` + любой из `--pack`, `--pack-type`,
`--pure-baseline`/`--no-pure-baseline`, `--init-side`, `--pack-setup`,
`--pack-check`, `--pack-exercise`, `--allow-baseline-tool` (в CLI или в самом
config-файле) — сразу `E_CONFIG_INVALID` с указанием конкретного
конфликтующего ключа. Обычные глобальные флаги (`--runs`, `--model`,
`--prompt`, `--verify`, `--judge`, таймауты, auth, форматы,
`--output`/`--workspace`, `--parallel`, `--baseline`, `--hint`) по-прежнему
переопределяют config-файл как обычно (CLI > config > default).

**Диск.** Раньше каждый прогон стоил `2 × runs` рабочих копий репо
(`apps/old|new/run-N`) плюс столько же изолированных `$HOME`. С N вариантами
цена растёт линейно: **`variants × runs`** рабочих копий, и каждая несёт свой
собственный `$HOME` — эксперимент из 4 вариантов × 3 прогона занимает **12**
копий приложения (плюс 12 HOME), не 6. Прежде чем поднимать `runs` или число
вариантов на большом репозитории — прикиньте место на диске заранее. На
практике HOME обычно тяжелее рабочей копии репозитория на порядок — пак,
чей `setup` реально ставит рантайм (venv, зависимости), может занять сотни
МБ – единицы ГБ на каждый HOME; сама рабочая копия небольшого репозитория —
единицы МБ. Считайте бюджет диска по HOME, а не по размеру тестируемого
репозитория (см. реальные цифры в примере 6 ниже).

### Паки, устанавливаемые через `setup`

Пак не обязан приносить с собой `SKILL.md`/agent/command/plugin-файлы —
`packs[].setup` вправе быть произвольной shell-командой, ставящей CLI/рантайм
в `$HOME` варианта (например `pipx install <пакет>`). Три вещи, которые
стоит знать про такой пак:

1. **Пак без файлов регистрации, но с `setup`, теперь не проваливает
   preflight.** Раньше пак без skill/agent/command/plugin-файлов, которые
   можно проверить, считался невалидным — «no registration instructions
   recorded». Теперь: нет файлов регистрации, но есть `setup` → прогон
   продолжается, но видимость этого пака НЕ подтверждается гейтами 4/5
   (`pack-visibility`/`foreign-pack-absent`) — в отчёте он помечен «видимость
   не подтверждена». Присутствие вместо этого доказывает `check` пака,
   запущенный гейтом 6 в каждом HOME. Пак без файлов регистрации И без
   `setup` — по-прежнему жёсткая ошибка (`E_PREFLIGHT_FAILED`, «visibility
   cannot be proven»). Реальный пример — graphify: в его репозитории нет
   `SKILL.md` (файл навыка генерирует собственный CLI пака при установке),
   поэтому нужен `type: "all"` в реестре, а не `"skill"` (см. пример 1 ниже
   и `E_PACK_INVALID_REF`, если перепутать).
2. **`setup` теперь заражает ВСЕ прогоны варианта одинаково, не только
   run-1.** `setup` выполняется один раз, с рабочим каталогом = app-каталог
   run-1 того же варианта. Всё, что он туда пишет (нетрекнутое или уже
   игнорируемое), копируется в app-каталог КАЖДОГО прогона того же
   варианта и исключается из измеряемого diff у всех них; после копирования
   отдельная проверка сверяет app-каталоги всех прогонов и обрывает
   эксперимент при расхождении. `setup`, изменивший ОТСЛЕЖИВАЕМЫЙ файл
   (не создавший новый, а поправивший существующий), обрывает эксперимент
   (`E_PACK_SETUP_FAILED`) — раньше это молча портило измеряемый diff.
   **Важно:** если шаг пака пишет в РАБОЧИЙ каталог репозитория (не в
   `$HOME`) — например `graphify opencode install`, кладущий `AGENTS.md` и
   плагин в клон репозитория, — он принадлежит `variants[].exercise`, не
   `packs[].setup`: `setup` гоняется один раз в общем `$HOME`, а
   `exercise` — per-run, в рабочем каталоге каждого прогона отдельно (см.
   пример 6 ниже).
3. **Docker-образ (`Dockerfile.opencode`) ставит `pipx`, а с ним Python** —
   `node:22-slim`, на котором собран образ, без единого Python не может
   поставить ни один PyPI-пак (`pip install` падает `error:
   externally-managed-environment`, а без Python вообще — exit 127). Если вы
   собрали образ ДО этого изменения — пересоберите:
   `bash scripts/build-docker-image.sh`, иначе `--isolation docker` с
   PyPI-based `setup` (например `pipx install graphifyy`) откажет.

## Проверенные примеры

Шесть сценариев, реально прогнанных и сверенных — команды ниже не выдуманы,
все флаги сверены с [таблицей параметров](#параметры-команды-run). Про
разложенные по дискам артефакты — см.
[«Структура результатов»](#структура-результатов) ниже.

### 1. Полный A/B на облачной модели, skill-пакет

Каноничный сценарий: сравнить репозиторий до/после установки skill-пакета.

```bash
./dist/testaipack run https://github.com/tarsy-club/TarSy-Bot \
  --pack "https://github.com/Graphify-Labs/graphify" --pack-type all \
  --prompt "составь подробную карту проекта и сохрани ее в файл MAP.md" \
  --model opencode/deepseek-v4-flash-free \
  --preflight-model opencode/deepseek-v4-flash-free \
  --pure-baseline --runs 2 --format html --collapse-repeats \
  --timeout-run 900 --timeout-verify 300 --timeout-install 300 --watchdog 90 \
  --workspace ./.testaipack --log-level info
```

Демонстрирует полный happy-path: клон → установка пакета → 2 прогона на
вариант → отчёт. `--pack-type all` здесь ОБЯЗАТЕЛЕН, не опция для
наглядности: голый git-URL без `--pack-type` детектируется как `skill`
автоматически (см. [«Форматы `--pack`»](#форматы---pack)), а в корне
репозитория graphify нет `SKILL.md` — файл навыка генерирует сам CLI пака
при установке, а не хранит репозиторий. С `--pack-type skill` этот пример
падает `E_PACK_INVALID_REF` («SKILL.md missing in pack»); `all` клонирует
репозиторий целиком и сканирует `skills/`/`agents/`/`commands/`/`plugins/`,
не считая их отсутствие ошибкой (см. «Форматы `--pack`» и «N-way примеры
пакетов, установленных через `setup`» ниже). Артефакты: `MAP.md` появится внутри
`apps/new/run-{1,2}/` (агент пишет его прямо в клон репозитория; `new` —
имя варианта с паком, `apps/new`, не `apps/newVersion` — суффикс `Version`
остался только в дереве прогонов, сделанных до n-way variants),
сравнительный отчёт — в
`.testaipack/<run-id>/results/{report.md,report.json,report.html}`.

### 2. Локальная модель (ollama), home-изоляция

```bash
./dist/testaipack run https://github.com/octocat/Hello-World \
  --prompt "Опиши в двух предложениях, что содержит этот репозиторий, и сохрани в файл SUMMARY.md" \
  --model ollama/qwen3.5-9b-32k --preflight-model ollama/qwen3.5-9b-32k \
  --runs 1 --pure-baseline --format html \
  --timeout-preflight 900 --timeout-run 1800 --watchdog 300 \
  --workspace ./.testaipack --log-level info
```

Ловушка: `--timeout-preflight` — отдельный таймаут auth-ping'а, не связанный
с `--timeout-run`/`--watchdog` (подробнее — в разделе «Локальные /
self-hosted модели» ниже, там же про поле `provider` в конфиге). На дефолте
`60` сек эта команда реально падала с
`E_PREFLIGHT_TIMEOUT: auth-ping timed out` — рассуждающая локальная модель не
укладывается в минуту даже с ответом в одно слово. Команда выше уже поднимает
таймаут заранее. Ожидайте: локальная модель заметно медленнее облачной —
закладывайте кратно больше времени, точных цифр не фиксировали.

### 3. Локальная модель в docker-изоляции

```bash
./dist/testaipack run https://github.com/octocat/Hello-World \
  --prompt "Опиши в двух предложениях, что содержит этот репозиторий, и сохрани в файл SUMMARY.md" \
  --model ollama/qwen3.5-9b-32k --preflight-model ollama/qwen3.5-9b-32k \
  --runs 1 --pure-baseline --format html \
  --timeout-preflight 900 --timeout-run 1800 --watchdog 300 \
  --isolation docker --docker-network host \
  --ide vscode --review-run 1 \
  --workspace ./.testaipack-docker --log-level info
```

Тот же прогон, что и в примере 2, но в `--isolation docker`. `--docker-network
host` здесь обязателен — без него preflight падает на auth-ping с connection
refused (причина и оговорка про Mac/Windows — в разделе «Локальные /
self-hosted модели» ниже).

### 4. Открыть результат в VS Code

```bash
./dist/testaipack review <run-id> --ide vscode --workspace ./.testaipack-docker
```

Двухшаговый процесс, который не очевиден: `--ide`/`--review-run` в `run`
только запекают предпочтение в `results/review.code-workspace` — сама
команда `run` редактор не запускает (фаза 12 всегда возвращает
`opened: false`). Реально открывает редактор отдельная команда `review` —
она делает `spawn(<ide-binary>, [review.code-workspace])`. Сгенерированный
workspace содержит по одному root'у на каждый вариант (`old run-N
(baseline)`, `new run-N`) плюс по одному на каждый пак реестра
(`PACK <name> (read-only)`) — в этом конкретном примере `--pack` не задан
(smoke-test), так что root'ов ровно два: `old run-N (baseline)`, `new run-N`.

### 5. Дешёвый smoke с JSON на stdout

```bash
./dist/testaipack run https://github.com/octocat/Hello-World \
  --prompt "reply with the word OK" --format json > report.json
```

`--format json` без `md` печатает в stdout содержимое `report.json`
байт-в-байт (весь progress уходит в stderr — см. `src/cli/progress.ts`),
поэтому команда пайпится в файл или дальше по конвейеру без хвостов
прогресс-лога.

### 6. N-way: три варианта одним прогоном (реально прогнано)

Реальный конфиг, которым прогнан трёхвариантный эксперимент — `baseline`
против `graphify` и `code-review-graph` (оба пакета продают одно и то же:
граф вызовов кода для навигации агента), на TarSy-Bot, в docker-изоляции, на
локальной модели через ollama. Сохраните как `.testaipack/config.json`:

```json
{
  "repoUrl": "https://github.com/tarsy-club/TarSy-Bot",
  "prompt": "добавь возможность работать с url в которыйх есть кирилица в человеко понятных url (chpu)",
  "hint": "Если в проекте есть готовый индекс кода (graphify или code-review-graph), используй его для навигации по коду; если его нет — работай как обычно.",
  "runs": 3,
  "parallel": 3,
  "baseline": "baseline",
  "isolation": "docker",
  "dockerImage": "testaipack-opencode:latest",
  "dockerNetwork": "host",
  "model": "ollama/qwen3.5-9b-32k",
  "preflightModel": "ollama/qwen3.5-9b-32k",
  "formats": ["md", "html"],
  "collapseRepeats": true,
  "timelineMode": "side-by-side",
  "judge": "Сравни варианты по приложенным патчам относительно базового: что сделано лучше или хуже в каждом и почему",
  "timeouts": {
    "preflightSeconds": 1200,
    "runSeconds": 3600,
    "watchdogSeconds": 300
  },
  "logLevel": "info",
  "packs": [
    {
      "name": "graphify",
      "ref": "https://github.com/Graphify-Labs/graphify",
      "type": "all",
      "setup": "pipx install graphifyy",
      "check": "graphify --version"
    },
    {
      "name": "code-review-graph",
      "ref": "https://github.com/tirth8205/code-review-graph",
      "type": "all",
      "setup": "pipx install code-review-graph"
    }
  ],
  "variants": [
    { "name": "baseline", "packs": [] },
    {
      "name": "graphify",
      "packs": ["graphify"],
      "exercise": "graphify opencode install && graphify extract . --code-only --no-cluster"
    },
    {
      "name": "code-review-graph",
      "packs": ["code-review-graph"],
      "exercise": "code-review-graph install --platform opencode && code-review-graph build"
    }
  ]
}
```

```bash
./dist/testaipack run --config ./.testaipack/config.json
```

Практические заметки, снятые с этого прогона:

- **`type: "all"`, не `"skill"`, для обоих паков.** `type: "skill"` ищет
  ровно один `SKILL.md` в корне репозитория пака — ни у graphify (файл
  навыка генерирует его собственный CLI при установке, в репозитории его
  нет вовсе), ни у code-review-graph (у него `SKILL.md` есть, но по семь
  штук, в подкаталогах `skills/*/`, не в корне) такого файла нет. `"all"`
  клонирует репозиторий целиком и сам решает, что регистрировать: для
  graphify `registeredIn` в итоге пуст — регистрировать нечего, это не
  ошибка; для code-review-graph находит все 7 `skills/*/SKILL.md`.
- **`setup` пака ставит рантайм в общий `$HOME`, `exercise` варианта пишет в
  рабочую копию репозитория** — это два разных места, и путать их нельзя.
  `pipx install graphifyy`/`pipx install code-review-graph` в `packs[].setup`
  выполняются один раз на пак, в изолированном `$HOME` варианта, объявившего
  пак. А `graphify opencode install` (пишет `AGENTS.md` и подключает плагин
  ПРЯМО В КЛОН репозитория) и `code-review-graph build` (строит
  `.code-review-graph/` per-workspace) обязаны быть `variants[].exercise` —
  они гоняются перед КАЖДЫМ прогоном, в рабочем каталоге именно этого
  прогона, не один раз на весь эксперимент.
- **`graphify extract` нужен `--code-only`**, иначе он видит только что
  написанный `graphify opencode install`-ом `AGENTS.md` как документ,
  требующий LLM-разбора, и падает без API-ключа. `--code-only` — offline,
  ключ не нужен: индексирует только код через tree-sitter (см. README
  graphify).
- **Диск: 9 рабочих копий + 9 HOME** (3 варианта × 3 прогона), но не в
  равной пропорции. В этом прогоне (TarSy-Bot — небольшой репозиторий)
  каждая рабочая копия заняла меньше 1.5 МБ, а каждый HOME — от ~220 МБ
  (`baseline`, только собственное состояние opencode) до ~615 МБ
  (`code-review-graph` — плюс venv и зависимости пакета); на весь вариант
  (3 прогона) HOME суммарно набежал до 1.8 ГБ. Бюджет диска считайте по
  HOME, не по размеру тестируемого репозитория.
- **`pack-visibility` для graphify честно репортует «не подтверждена».**
  Реальная строка из `preflight.log` этого прогона: `pack 'graphify'
  delivered via setup (no registration instructions) for variant 'graphify'
  — visibility not confirmed by gate 4; presence is instead proven by gate
  6's check command` (см. «Паки, устанавливаемые через `setup`» выше) — это
  ожидаемо для пака без файлов регистрации, не повод для тревоги, покуда у
  пака задан `check` и гейт 6 зелёный.
- Реальный заголовок сводки из этого отчёта (обе метрики выросли у обоих
  паков — прогон ollama-модели на конкретном промпте, не общий вывод про
  сами пакеты): `По сравнению с baseline: graphify — нет значимых различий
  (0 лучше, 4 хуже, всё в пределах шума); code-review-graph — нет значимых
  различий (0 лучше, 4 хуже, всё в пределах шума).`

## Параметры команды `run`

Команда `run` принимает собственные CLI-флаги (перечислены первыми) и
форвардит в парсер фазу-00 все остальные опции конфигурации прогона.

### Собственные флаги `run`

| Флаг              | Тип                                              | По умолчанию | Описание                                                          |
| ----------------- | ------------------------------------------------ | ------------ | ----------------------------------------------------------------- |
| `--review-run <N>`| `int`                                            | `1`          | Какой из N прогонов показать в `review` (`run-N` в путях каждого варианта). Вне диапазона `1..runs` → warning и откат на `1`, а не fail. |
| `--ide <editor>`  | `vscode\|cursor\|code-insiders`                  | `vscode`     | Какой редактор запишется в команду открытия `review.code-workspace`. Сам `run` редактор не открывает — только запекает предпочтение; открывает уже отдельная команда `testaipack review`. Не валидируется как enum: любое другое значение молча трактуется как `vscode` (`code`), без ошибки. |
| `--ephemeral` / `--no-ephemeral` | флаг                              | off          | Удалить `apps/`, `home/`, `gitdirs/`, `pack/` после прогона (оставить `results/`). |
| `--config <path>` | `string`                                         | —            | Путь к `config.json` testaipack. CLI-флаги всё равно побеждают значения из файла — `--config` подставляет дефолты, а не переопределяет то, что явно передано в командной строке. |

### Флаги конфигурации прогона (phase-00)

| Флаг                       | Тип                                       | По умолчанию                  | Описание                                                                                                         |
| -------------------------- | ----------------------------------------- | ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `<repo>` (позиционный)     | `string`                                  | — (обязательный)              | URL git-репозитория для A/B прогона.                                                                             |
| `--pack <ref>`             | `string`                                  | —                             | Тестируемый пакет: git-URL, npm-pkg, локальный путь или `mcp:<name>:<config>`. Тип определяется автоматически.    |
| `--pack-type <type>`       | `skill\|plugin\|agent\|command\|mcp\|all` | авто                          | Переопределить тип пакета вместо авто-детекции.                                                                  |

### Какая модель за что отвечает

Два разных флага контролируют две разные модели — их легко перепутать:

| Флаг               | Чья это модель                          | Если флаг не задан                                    |
| ------------------- | ---------------------------------------- | ------------------------------------------------------ |
| `--model`           | Модель самого прогона (глобальный дефолт для каждого варианта) | Ambient-модель из `~/.config/opencode/opencode.json`   |
| `--preflight-model` | Модель только для LLM-судьи (`--judge`) | Судья идёт без явной модели (ambient-дефолт opencode)  |

Preflight (если не отключён `--no-preflight`) пингует **ровно ту модель, которую
получит сам прогон** — то есть `--model`, если он задан, иначе ту же
ambient-модель, что и прогон. Раньше preflight пинговал `--preflight-model`, а
прогон при этом молча уходил на ambient-модель — здоровый дешёвый пинг мог
пройти, пока сам прогон падал на исчерпанной/неаутентифицированной модели, и это
обнаруживалось только косвенно: через 90-секундный watchdog на каждом прогоне
каждого варианта. Теперь такое рассогласование ловится preflight-ом за ≤60 секунд, а не
после того как деньги и время на прогон уже потрачены — если вы явно
переключаете провайдера/модель для прогона, задавайте `--model`, а не
`--preflight-model`.

## Пересборка отчёта офлайн (`report --rebuild`)

`testaipack report <run-id> --rebuild` пересчитывает aggregate → diff →
timeline → report (фазы 07/08/10/11) заново по артефактам, уже лежащим на
диске — без повторного запуска агента, без обращения к LLM и без docker.
Судья по умолчанию не переспрашивается: существующий `judge.json` просто
переиспользуется как есть.

Для рабочих деревьев старше появления `run-input.json` недостающие входные
данные восстанавливаются из `manifest.json`/`config/*.json`, либо (если не
восстановились) берут значение флага ниже, либо документированный дефолт —
каждое восстановленное / переданное / дефолтное поле раскрывается отдельной
секцией в пересобранном отчёте.

Работает и на воркспейсах, сделанных **до** появления n-way variants (без
`schemaVersion` в `manifest.json`) — они читаются через слой совместимости и
автоматически получают варианты `old`/`new`; пересобранный `report.json`
записывается уже в текущей форме (`schemaVersion: 2`), см.
[«Миграция на schemaVersion 2»](#миграция-на-schemaversion-2).

| Флаг                        | Тип                                       | По умолчанию | Описание                                                          |
| ---------------------------- | ------------------------------------------ | ------------ | ------------------------------------------------------------------ |
| `--force`                    | флаг                                       | off          | Разрешить перезаписать уже существующий `report.json`.             |
| `--rejudge`                  | флаг                                       | off          | Единственное opt-in исключение из «rebuild не вызывает LLM»: разрешает ровно один живой вызов судьи над пересобранным diff'ом. |
| `--judge <text\|@file>`      | `string`                                  | —            | Только вместе с `--rejudge` — инструкции для этого одного вызова судьи (без `--rejudge` используется лишь как disclosure-подсказка, судья не вызывается). Без значения — инструкции берутся из исходного `run-input.json`. |
| `--format <f>...`            | `md\|html\|json\|yaml` (повторяется)      | —            | Форматы отчёта, если не восстановились из `run-input.json`.        |
| `--pricing-path <path>`      | `string`                                   | —            | Таблица цен, если не восстановилась из `run-input.json`.           |
| `--diff-html` / `--no-diff-html` | флаг                                   | —            | Генерировать ли `diff/*.html`, если не восстановилось.             |
| `--collapse-repeats` / `--no-collapse-repeats` | флаг                     | —            | Схлопывать ли повторы tool-call на таймлайне, если не восстановилось. |
| `--timeline-mode <m>`        | `side-by-side\|tree-diff\|merged`         | —            | Раскладка таймлайна, если не восстановилась.                       |

## Устранение неполадок

**`E_EXPORT_INVALID` (изредка, на прогонах без других ошибок).** `opencode
export` иногда отдаёт обрезанный JSON сразу после чистого завершения прогона —
внутреннее хранилище сессии ещё не успело дозаписаться. Фаза `run-side`
переспрашивает export с ограниченным экспоненциальным backoff (несколько
попыток, буквально пара секунд суммарно) и только если export по-прежнему
невалиден после всех попыток — фейлит прогон этим кодом. Если вы видите
`E_EXPORT_INVALID` — это не транзиентный сбой самого testaipack, а то, что
export оставался обрезанным ещё через несколько попыток; стоит проверить
версию/состояние `opencode`.

**Здоровый прогон помечен `rateLimited`/провалом, хотя видимых проблем нет.**
Детекция rate-limit смотрит только на текст ассистента и на вывод упавшего
tool-вызова — не на весь JSON события целиком. Если раньше у вас бывали
прогоны, ошибочно помеченные rate-limit-ом просто из-за случайной подстроки
«429» где-то в данных (например, в `callID` или в содержимом прочитанного
файла) — так больше не происходит; если флаг всё-таки выставлен, значит в
потоке действительно был текст, похожий на ошибку rate-limit.

**Прогон завис/упал по watchdog, хотя preflight прошёл успешно.** Скорее
всего preflight пинговал не ту модель, которую увидел сам прогон — см.
[«Какая модель за что отвечает»](#какая-модель-за-что-отвечает) выше и задайте
`--model` явно.

**В логах/ошибках больше не видно секретов из `mcp:`-пакетов и приватных
git-URL.** Если пакет задан как `mcp:<name>:{...}` с токеном в секции `env`,
или репозиторий клонируется по URL с `user:token@host` — ни то ни другое
теперь не попадает в текст ошибки или в `install.log`: `mcp`-рефы в
диагностике усечены до `mcp:<name>`, а credentials из URL вычищены. Если для
диагностики реально нужен полный конфиг pack-а — смотрите его в
`config/<variant>.json` (там он уже применён к конкретному варианту, а не в
сыром виде).

**`testaipack report <run-id>` / `compare` не находят прогон, сделанный с
`--output`.** `--output <path>` переносит `report.*`, `metrics.json`,
`timeline.*` и `diff/` в указанный каталог, но команды `report`/`compare`/
`review`/`list` всегда читают отчёт по канонической схеме
`<workspace>/<run-id>/results/report.json` — про кастомный `--output`-путь они
не знают вообще. Если нужно смотреть прогон через `report`/`compare` по его
run-id — не используйте `--output`; если `--output` всё же нужен (например,
чтобы сложить отчёт в определённое место для CI), читайте его оттуда
напрямую, а не через run-id-команды.

### Локальные / self-hosted модели (например, ollama)

Чтобы прогнать testaipack на локальной модели, нужны две вещи одновременно —
без любой из них прогон либо не увидит модель, либо упадёт ещё до первого
реального прогона.

**1. Модель и её provider должны быть в реальном
`~/.config/opencode/opencode.json`.** Фаза home-isolation копирует
поля `provider`, `small_model`, `enabled_providers`, `disabled_providers` из
этого файла в изолированные HOME КАЖДОГО варианта — целиком и идентично на
всех вариантах (см. [«Структура результатов»](#структура-результатов)). Раньше
локально настроенный provider внутри изолированного прогона был не виден
вообще, даже если `model` указывал именно на него. Пример конфига с ollama:

```json
{
  "model": "ollama/qwen3.5:9b",
  "provider": {
    "ollama": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Ollama (local)",
      "options": { "baseURL": "http://localhost:11434/v1" },
      "models": { "qwen3.5:9b": { "name": "Qwen3.5 9B" } }
    }
  }
}
```

**2. Модель для самого прогона задаётся флагом `--model <provider>/<model>`** —
той же моделью пингует и preflight, см.
[«Какая модель за что отвечает»](#какая-модель-за-что-отвечает) выше.

**С `--isolation docker` на Linux добавьте `--docker-network host`** —
иначе контейнер обращается к `http://localhost:11434` сам к себе, а не к
хосту, потому что ollama слушает только `127.0.0.1` хоста и не виден через
дефолтный bridge. **Только Linux**: на Docker Desktop для Mac/Windows
`--network host` не даёт контейнеру loopback хоста так же — там это не
работает, нужен другой способ (например `host.docker.internal`, если
сервер слушает не только `127.0.0.1`).

**3. `--timeout-preflight` — отдельный таймаут, про него легко забыть.**
Preflight-гейт `auth-ping` отправляет тривиальный промпт «reply with the single
word OK», но у него свой собственный таймаут — `--timeout-preflight` (по
умолчанию `60` сек), никак не связанный с `--timeout-run` или `--watchdog`.
Reasoning-тяжёлые модели (в том числе многие локальные) могут потратить на
рассуждение перед этим единственным словом-ответом заметно больше 60 секунд —
тогда прогон падает с `E_PREFLIGHT_TIMEOUT: auth-ping timed out`, не дойдя ни
до одного реального прогона. Для медленной локальной модели поднимайте
`--timeout-preflight` **вместе с** `--timeout-run`/`--watchdog`, а не вместо
них:

```bash
./dist/testaipack run <repo> --prompt "реализуй фичу X" \
  --model ollama/qwen3.5:9b \
  --timeout-preflight 300 \
  --timeout-run 1800 \
  --watchdog 300
```

## Форматы `--pack`

Тип пакета определяется по префиксу `--pack` (или фиксируется через `--pack-type`):

| Ссылка                                               | Тип      | Что тестируется                                                             |
| ---------------------------------------------------- | -------- | --------------------------------------------------------------------------- |
| `github:owner/skill` / `git+https://…` / лок. путь   | `skill`  | skill-пакет (каталог с `SKILL.md`).                                         |
| `npm:myplugin`                                       | `plugin` | npm-модуль opencode-плагина (ставится через `opencode plugin`).             |
| `agent:./build.md` / `agent:<git-url>`               | `agent`  | одиночный агент (`.md`).                                                    |
| `command:./run.md`                                    | `command`| одиночная команда (`.md`).                                                  |
| `mcp:myserver:{"command":"npx","args":["-y","srv"]}` | `mcp`    | MCP-сервер: конфиг инлайн (v0.3).                                           |
| `mcp:myserver:@./mcp.json`                            | `mcp`    | MCP-сервер: конфиг из файла (v0.3).                                         |
| `--pack-type all` (в паре с git-URL/лок. путём репо) | `all`    | Весь репозиторий пакета целиком: обходит стандартные подпапки `skills/`, `agents/`, `commands/`, `plugins/` и регистрирует каждую найденную секцию. |

MCP-конфиг вписывается в секцию `mcp` сгенерированного `opencode.json` КАЖДОГО
варианта, объявившего этот пак (`mcp.<name>`); варианты, не объявившие его,
MCP-сервер не получают.

## Сравнение двух прогонов (`compare`)

`compare` сопоставляет **любые два прогона** между собой, а не только внутри
одного прогона. Удобно для вопросов «pack-X неделю назад vs сейчас» или
«pack-X vs pack-Y». Команда берёт выбранный вариант каждого прогона и считает
дельты (токены, время, стоимость, ранг успеха) через тот же движок, что и
основной отчёт: run 1 играет роль baseline, run 2 сравнивается против него.

| Флаг                       | По умолчанию | Описание                                                                                                          |
| -------------------------- | ------------ | ----------------------------------------------------------------------------------------------------------------- |
| `<run-id-1>` (позиционный) | —            | Первый прогон (играет роль baseline).                                                                             |
| `<run-id-2>` (позиционный) | —            | Второй прогон (сравнивается против первого; дельты = run2 minus run1).                                            |
| `--variant <name\|best>`   | `best`       | Какой вариант брать в ОБОИХ прогонах: имя варианта (например `graphify`) или `best` — вариант с наивысшим медианным successRank. |
| `--variant2 <name\|best>`  | значение `--variant` | Переопределяет выбор ВТОРОГО прогона независимо от `--variant` — нужно, когда прогоны используют разные наборы имён вариантов (например сравнение старого v1-прогона, у которого только `old`/`new`, с новым v2-прогоном с произвольными именами). |
| `--perspective <p>`        | —            | Устаревший скрытый алиас `--variant`, применяется симметрично к обоим прогонам: `new-vs-new` → `--variant new`, `old-vs-old` → `--variant old`, `best`/`auto` → `--variant best`. Оставлен ради существующих скриптов. |
| `--format <f>`             | `md`         | Формат вывода: `md` (Markdown-таблица) или `json`.                                                                |
| `--workspace <path>`       | `.testaipack`| Корень рабочего дерева testaipack.                                                                                |

```bash
# Одинаковый вариант в обоих прогонах
./dist/testaipack compare 2026-07-21_17-30-0a1b2c 2026-07-23_10-15-def456 \
  --variant new

# Разные наборы имён — старый v1-прогон (old/new) против нового N-way (a/b/c)
./dist/testaipack compare 2026-07-21_17-30-0a1b2c 2026-07-23_10-15-def456 \
  --variant new --variant2 b
```

`compare` открывает **и v1-, и v2-прогоны** одинаково: v1-воркспейс без
`schemaVersion` автоматически подставляет варианты `old`/`new` через слой
совместимости (см. [«Миграция на schemaVersion 2»](#миграция-на-schemaversion-2))
— имя `old`/`new` в `--variant`/`--variant2` работает на нём точно так же, как
на прогоне, реально созданном легаси-шимом.

## Структура результатов

После прогона всё лежит под `./.testaipack/<run-id>/`. Дерево (без
`--ephemeral`, N-way пример — 3 варианта `old`/`graphify`/`ast-grep`,
реестр из 2 паков):

```
.testaipack/
└── <run-id>/                      # 2026-07-23_10-15-0a1b2c
    ├── manifest.json              # конфигурация прогона, schemaVersion: 2 (фаза 01)
    ├── run-input.json             # resolved RunInput (для report --rebuild)
    ├── apps/
    │   ├── source/                # один clone репозитория (шаблон для копий ниже)
    │   ├── old/run-{1..N}/        # рабочие копии варианта old (баз. имя, без old/newVersion)
    │   ├── graphify/run-{1..N}/   # рабочие копии варианта graphify
    │   └── ast-grep/run-{1..N}/   # рабочие копии варианта ast-grep
    ├── pack/                      # реестр установленных паков
    │   ├── graphify/              # доставленный пак "graphify"
    │   └── ast-grep/              # доставленный пак "ast-grep"
    ├── home/                      # фейковые $HOME (изоляция), по каталогу на вариант
    │   ├── old/run-{1..N}/
    │   ├── graphify/run-{1..N}/
    │   └── ast-grep/run-{1..N}/
    ├── gitdirs/                   # перенесённый .git на вариант, только при --protect-git
    ├── config/                    # сгенерированные opencode.json, по файлу на вариант
    │   ├── old.json
    │   ├── graphify.json
    │   └── ast-grep.json
    └── results/                   # все отчётные артефакты (переезжают вместе с --output)
        ├── raw/                   # opencode export сырых прогонов (фаза 06; НЕ переезжает с --output)
        │   ├── old/run-N.json, run-N.events.ndjson, run-N.result.json
        │   ├── graphify/...
        │   └── ast-grep/...
        ├── diff/                  # git-diff по прогонам (фаза 08)
        │   ├── old/run-N/full.patch, summary.json (+ variant.html при --diff-html)
        │   ├── graphify/...
        │   └── ast-grep/...
        ├── metrics.json           # агрегированные метрики, MetricsReport (фаза 07)
        ├── timeline.json          # карта событий, lanes: N (фаза 10)
        ├── timeline.html
        ├── report.md              # отчёты во всех запрошенных форматах (фаза 11)
        ├── report.html
        ├── report.json
        ├── report.yaml
        ├── judge.json             # N-way вердикт LLM-судьи, если задан --judge (фаза 09)
        ├── judge.log              # полный stdout+stderr вызова(ов) судьи, если она реально запускалась (фаза 09)
        ├── install.log            # лог доставки паков (фаза 03)
        ├── pack-setup.log         # лог setup/check/exercise (фаза 04b), если что-то из них задано
        ├── prep.json              # PrepReport: setup/check/exercise-эвиденс по пакам и вариантам
        ├── preflight.log          # лог preflight-гейтов (фаза 05), если он включён
        ├── gc.log                 # лог удаления при --ephemeral (фаза 13)
        └── review.code-workspace  # multi-root VSCode workspace, папка на вариант + на пак (фаза 12)
```

С классическим двусторонним вызовом (без `variants` в конфиге) варианты
всегда называются `old`/`new`, так что дерево выглядит как раньше, только
`apps/old`/`apps/new` — без хардкод-суффикса `Version` (`oldVersion`/
`newVersion` остались только в дереве прогонов, реально СОЗДАННЫХ до этой
версии — см. [«Миграция на schemaVersion 2»](#миграция-на-schemaversion-2)).

Флаг `--ephemeral` удаляет `apps/`, `home/`, `gitdirs/`, `pack/` сразу после
прогона, оставляя `results/` (включая `raw/`) и `manifest.json`.

`--output <path>` перенаправляет отчётные артефакты (`report.*`, `metrics.json`,
`timeline.*`, `diff/`, `judge.json`, `judge.log`, `review.code-workspace`, `preflight.log`,
`install.log`, `pack-setup.log`, `prep.json`, `gc.log`) в указанный каталог вместо `results/`.
Manifest и всё рабочее дерево (`apps/`, `home/`, `gitdirs/`, `pack/`, `config/`) остаются под
`<workspace>/<run-id>/`, а вот `raw/` (сырые opencode-экспорты) — особый случай:
он физически лежит внутри `results/` и с `--output` НЕ переезжает, оставаясь по
пути `<workspace>/<run-id>/results/raw/`.

## Миграция на schemaVersion 2

N-way variants поменяли wire-формат `report.json`/`manifest.json`/
`run-input.json`: теперь у каждого из трёх лежит поле `schemaVersion: 2`.
Отсутствие поля — признак «сделано до этой версии» (`schemaVersion: 1`).

**Что реально ломается.** Если у вас есть внешний скрипт, читающий
`report.json` напрямую (не через `testaipack compare`/`report`), и он
обращается к полю `metricsDiff.old`/`metricsDiff.new`/`metricsDiff.deltas`/
`metricsDiff.bothFailed` — он сломается на новых прогонах. Эта форма
заменена на:

```jsonc
// было (v1)
{ "metricsDiff": { "old": {...}, "new": {...}, "deltas": {...}, "bothFailed": false } }

// стало (v2)
{
  "metrics": {
    "baseline": "old",
    "variants": [ /* VariantAggregates по каждому варианту, порядок конфига, baseline включён */ ],
    "deltas":   [ /* VariantDelta по каждому НЕ-baseline варианту против baseline */ ],
    "allFailed": false
  }
}
```

Что читать вместо старых полей:
- `metricsDiff.old` → `metrics.variants.find(v => v.variant === metrics.baseline)`.
- `metricsDiff.new` → `metrics.variants.find(v => v.variant === <нужное имя>)`.
- `metricsDiff.deltas` → `metrics.deltas.find(d => d.variant === "new").deltas`
  (в легаси-шиме единственный не-baseline вариант по-прежнему называется
  `new`; в N-way — по одной записи на каждый не-baseline вариант).
- `metricsDiff.bothFailed` → `metrics.allFailed`.

Аналогично `diff: {old, new}` → `diffs: DiffResult[]` (ищите по `variant`),
`timeline: {old, new}` → `timeline.lanes: VariantTimeline[]`,
`judge.oldQuality`/`judge.newQuality` → `judge.scores: [{variant, quality}, ...]`
+ `judge.ranking: string[]`, `summary.improvements/regressions/neutral`
(плоские) → `summary.perVariant: VariantSummary[]` (по записи на не-baseline
вариант). `side`/`Side` исчезли из контракта целиком — везде, где раньше было
`side: "old" | "new"`, теперь `variant: string`.

**Что НЕ ломается.**
- **Старые (v1) воркспейсы продолжают открываться.** `testaipack report
  <run-id> --rebuild`, `compare`, `list` читают workspace без
  `schemaVersion` через слой совместимости и автоматически подставляют
  варианты `old`/`new` — вы не обязаны ничего мигрировать вручную, чтобы
  посмотреть старый прогон.
- **Классический CLI не меняется**: `--pack`/`--prompt`/`--pure-baseline`/…
  работают как раньше и по-прежнему пишут `report.json`, только теперь со
  `schemaVersion: 2` внутри и в новой форме `metrics`/`diffs`/etc — если ваш
  скрипт читает отчёт **через** `testaipack compare`/`report --rebuild`, а не
  напрямую парсит JSON, для вас ничего не изменилось.
- Пересобрать v1-прогон в v2-форму: `testaipack report <run-id> --rebuild`
  запишет `report.json` уже со `schemaVersion: 2` (провенанс
  `flagDefaults.migratedFromV1: true` в манифесте отмечает, что прогон
  мигрирован, а не сделан этой версией нативно).

## Язык отчёта

С v0.8.0 сгенерированный отчёт **на русском**: `report.md`, `report.html`,
`timeline.html`, вывод `testaipack compare`, заголовок сводки, раздел
provenance при `report --rebuild` (и его пер-полевые заметки о
восстановленных значениях), текст деталей сигналов contamination. Если вы
парсите эти файлы КАК ТЕКСТ (grep по заголовку секции, поиск фразы вроде
`vs base: …`) — на прогонах v0.8.0+ это сломается; мы наткнулись на это
сами (см. CHANGELOG 0.8.0, `report --rebuild` искал английский заголовок
`## Summary` и подставлял provenance-блок не туда, пока отчёт не стал
русским).

**Что НЕ меняется:**

- `report.json`/`report.yaml` — имена полей остаются английскими
  (`headlineResult`, `variant`, `significant`, `better`, …), `schemaVersion`
  не бампается. Единственное исключение — само ЗНАЧЕНИЕ поля
  `summary.headlineResult`: это строка, а не структура контракта, и она
  на русском, как в md/html.
- Терминальный вывод самого CLI — строки прогресса `run`, вывод
  `gc`/`doctor`/`list`, сообщения об ошибках валидации конфига — остаются
  английскими. Это осознанная граница: report-рендер адресован человеку,
  читающему готовый отчёт; вывод CLI — терминалу/логам, где инструмент
  по умолчанию говорит по-английски.

Если вам нужен отчёт на английском для существующей автоматизации — читайте
`report.json`/`report.yaml` напрямую (структура/имена полей стабильны) или
рендерите свой Markdown из него; сам инструмент переключателя языка не
имеет.

## Архитектура

Пайплайн разбит на 14 нумерованных фаз плюс одна ненумерованная (`04b`),
каждая описана отдельным TypeSpec-контрактом и phase-документом. Полная схема
зависимостей — в [`docs/phases/README.ru.md`](docs/phases/README.ru.md).

```
00-cli-parse → 01-workspace-setup → 02-repo-clone → 03-pack-install
→ 04-home-isolation → 04b-pack-setup → 05-preflight
→ 06-run-side (× runs × N вариантов, до --parallel одновременно)
→ 07-aggregate → 08-diff → 09-judge → 10-timeline
→ 11-report-render → 12-review-workspace → 13-cleanup
```

- **Контракт:** `contract/` — TypeSpec; компилируется в JSON Schema →
  `src/generated/` (TS-типы + Zod-схемы). Единственный источник правды для
  типов. Wire-формат — `schemaVersion: 2` (n-way variants); совместимость со
  старыми (v1) артефактами — `src/compat/legacy.ts` +
  `src/compat/v1-schemas.ts` (замороженная копия дореформенных схем).
- **Изоляция:** фейковый `$HOME` целиком строит `src/phases/04-home-isolation.ts`,
  по одному дереву на каждый вариант. Режим `--isolation=docker` прогоняет
  opencode в throwaway-контейнере (`src/isolation/docker-runner.ts`): хост-`$HOME`
  монтируется как `/home/opencode`, рабочая директория — как `/workspace`. При
  недоступном Docker daemon (фаза 00, `isDockerAvailable`) запуск автоматически
  откатывается на `home`-изоляцию и печатает предупреждение в stderr.
- **Метрики:** `src/metrics/` — извлечение из opencode-export, медиана/IQR,
  правило 1.5×IQR для значимости, всегда против IQR baseline-варианта.
- **Цены:** `src/pricing/pricing.json` — USD за 1M токенов по провайдерам.
- **Стек:** TypeScript strict + Effect-TS (IO и типизированные ошибки) + Zod
  (runtime-валидация) + TypeSpec (контракт) + bun (сборка).

## Разработка

Перед первой правкой прочитайте [`CONTRIBUTING.ru.md`](CONTRIBUTING.ru.md) — там
зафиксированы правила: **TDD** (тесты первыми, красный → зелёный), **контракты
первичны** (правка `contract/*.tsp` → `tsp compile` → codegen → impl), порог
**coverage ≥80%** (CI gate) и анти-rework-процедура (локально зелёные `typecheck`
+ `lint` + `test` перед push). Кратко: поведение меняется через контракт, тесты
пишутся до impl, `src/generated/` не правится руками.

```bash
# Зависимости
npm install
npm --prefix contract install

# Сгенерировать типы из контракта (обязательный шаг — npm install сам его не запускает)
npm run contract:codegen

# Проверки
npm run typecheck     # tsc --noEmit (strict + noUncheckedIndexedAccess + exactOptionalPropertyTypes)
npm run lint          # eslint (flat config, type-aware, --max-warnings=0)
npm test              # vitest run
npm run test:coverage # vitest с покрытием (≥80% — gate в CI)

# Сборка бинарника (нужен bun)
npm run build         # → dist/testaipack

# Разработка с hot-reload
npm run dev           # tsx watch bin/testaipack.ts

# Форматирование
npm run format        # prettier --write .
```

**Требования:** Node `>=22`, bun `>=1.1` (для сборки). TypeSpec-компилятор
ставится как devDependency.
